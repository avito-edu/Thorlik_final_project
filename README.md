# **Итоговое задание по программированию на Go**

## **Введение**

Вы — член кросс-функциональной команды в Авито. В этом семестре вам нужно подготовить ядро сервиса, которое реально можно запустить на сервере: с пользователями и ролями, устойчивой БД, миграциями, логами и фоновыми задачами. Цель — не «пэт‑проект», а минимальный, но честный прод, поверх который уже в следующем семестре вы будете реализовывать мобильное приложение, уже в роли мобильного разработчика.

Вы выбираете домен, формулируете user stories, реализуете ролевую модель, а также бизнес‑правила с учетом наших функциональных требований.

## **1\. Этапы работы**

### **Этап 1\. Предварительное согласование**

* **«Значимые» use cases:** 3–6 ключевых сценариев, описывающих предметную область и роли пользователей.  
* **Component diagram (C4, уровень Component):** основные компоненты (handlers, services, repositories, DB, worker/cron), внешние интеграции и их связи.  
* **Короткое описание домена:** 1–2 абзаца, ключевые ограничения и предположения.

### **Этап 2\. Ревью**
На данном этапе предстоит пройти заочное ревью и сделать правки

### **Этап 2\. Сдача**
На этапе сдачи студент очно демонстрирует работоспособность системы в соответствии с критериями приемки


## **2\. Выбор предметной области**

*Примеры (для ориентира; использовать их нельзя — выберите другой домен):*

1. **Task Manager с ролевой моделью**: админ, менеджер, пользователь; задачи, статусы, назначение.  
2. **File Processor**: загрузка и фоновая обработка изображений или CSV, статусы, выдача результата.  
3. **Booking System**: ресурсы и слоты, бронь, отмена, контроль конфликтов.  
4. **News Aggregator**: добавление RSS‑лент, периодическое обновление, статьи, отметки прочитано/избранное.  
5. **Сервис для образовательного процесса**: роли преподаватель и студент, курсы, записи на курсы.

***Выберите любой реальный домен или вдохновляйтесь системами из сериалов, фильмов, игр или реальной жизни — при условии соблюдения требований ниже.***

## **3\. Функциональные требования**

### **Финальный артефакт раздела**

Итогом этого раздела должны стать: **таблица соответствия** и оформленные **критерии приёмки (Given — When — Then)** по каждой user story. В таблице укажите связанные эндпоинты, доменные бизнес‑правила, юнит‑тесты и негативные кейсы. Рекомендуемые колонки таблицы:

* Story ID  
* Краткое описание  
* Эндпоинты  
* Критерии приёмки (Given — When — Then)  
* Бизнес‑правила (что разрешено/запрещено по предметной области)  
* Юнит‑тесты (ключевые позитивные проверки)  
* Негативные кейсы (валидация/права/конфликты)

### **User stories**

Подавайте истории в формате: *As a \<роль\> I want \<действие\> so that \<ценность\>*.

**Критерии приёмки оформляйте по шаблону «Given — When — Then»**:

* **Given** — исходные условия: роли/права, данные в БД, конфигурация.  
* **When** — действие пользователя/системы: HTTP‑вызов, запуск воркера, обработка события.  
* **Then** — наблюдаемый результат: код ответа/тело, изменение состояния в БД, запись в лог, постановка задачи в очередь.

### **Бизнес‑правила (как их понимать и фиксировать)**

Это **доменные ограничения и инварианты**, которые сервис обязан соблюдать **независимо от транспорта**. Они проверяются в **сервисном слое** и объясняют, почему вы отдаёте 403/409/422 и т. п.

* Примеры: «только менеджер/админ может создать задачу»; «статус меняется только по допустимым переходам»; «нельзя бронировать пересекающиеся слоты»; «дедлайн не в прошлом»; «размер файла ≤ N MB»; «у статьи уникальный URL в пределах фида».  
* Если правило нарушено — явно укажите ожидаемую реакцию: «вернуть 400/403/409 с кодом ошибки».  
* Чек‑лист: (1) проверяемо юнит‑тестом сервиса; (2) не зависит от HTTP; (3) однозначно трактуется.

### **Функциональные требования (что сдаётся в этом разделе)**

* **Аутентификация и авторизация с ролевой моделью.**  
* **Пользователь** как доменная сущность (создание/получение минимум).  
* **Основная доменная сущность**: операции Create, List (с пагинацией), GetByID.  
* **Не менее двух бизнес‑правил**, проверяемых в сервисах (с негативными сценариями).  
* **Таблица соответствия** на каждую историю: эндпоинты и тест‑кейсы (см. формат ниже).

### **Таблица соответствия — пример**

| Story ID | Краткое описание | Эндпоинты | Критерии приёмки (GWT) | Бизнес‑правила | Юнит‑тесты | Негативные кейсы |
| :---- | :---- | :---- | :---- | :---- | :---- | :---- |
| ST‑1 | Менеджер создаёт задачу | POST /tasks | Given роль=manager и валидный payload — When POST /tasks — Then 201 и task.id создан | Только менеджер/админ; дедлайн не в прошлом | TestTaskCreate\_Success; TestTaskCreate\_DeadlinePast | 400 невалидный дедлайн; 403 по ролям |
| ST‑2 | Пользователь видит свои задачи | GET /tasks?assignee\_id=me | Given аутентифицирован — When GET /tasks?assignee\_id=me — Then 200 только свои задачи; пагинация | Фильтрация по назначенному; сортировка по due\_at | TestTasksList\_ByAssignee; TestTasksList\_Pagination | 401 без токена; 403 при попытке чужого списка |
| ST‑3 | Пользователь меняет статус задачи | PATCH /tasks/{id}/status | Given владелец задачи — When PATCH status todo→in\_progress — Then 200; запись в логе аудита | Допустимые переходы статусов; лог аудита | TestTaskStatus\_Transitions; TestTaskStatus\_Audit | 400 недопустимый переход; 404 не найдена |
| ST‑4 | Админ назначает роль пользователю | PATCH /users/{id}/role | Given роль=admin — When PATCH роль — Then 200; роль изменена | Только админ может менять роли | TestUserRole\_UpdateByAdmin | 403 не админ; 404 нет пользователя |

### **Минимальный набор эндпоинтов (адаптируйте под домен)**

* GET /health  
* POST /users; GET /users/{id}; GET /users  
* Доменные: POST /{entity}; GET /{entity}; GET /{entity}/{id}  
* Единый формат ошибок (например, `{code, message, details}`); корректные HTTP‑коды (не только 200/500)

**Примечание:** мобильный клиент на момент сдачи не требуется. Просто держите в уме, что API затем должен комфортно поддержать минимум пару экранов.
